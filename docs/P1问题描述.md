# P1 问题分析（重写版）

> 本文件是对「P1 = SAC 温度初始化 1e-2 是否导致不收敛」的最终再评估，供后续 Agent 复核。
> 定位范围：仅训练侧代码体检，不含环境/硬件，不修改任何代码。
> 结论一句话：**P1 机制属实但被上一版分析高估了，正确级别是「次要调参项」；真正决定本轮重启成败的是第 5 节的 manifest + demo buffer cache 数据链路，而非温度。**

---

## 1. P1 是什么

事实链（代码核对属实）：

- `SACAgentHybridSingleArm.create_pixels` 的默认是 `temperature_init=1.0`（`sac_hybrid_single.py:574`，继承上游 SAC 库默认）；
- 但真机入口 `launcher.make_sac_pixel_agent_hybrid_single_arm` **显式传 `temperature_init=1e-2`**（`launcher.py:133`）；
- 策略方差在 `Policy.__call__` 里是 `stds * jnp.sqrt(temperature)`（`actor_critic_nets.py:164`）。

因此初始 α=0.01 → `sqrt(0.01)=0.1`，初始动作噪声是 α=1 时的 1/10。

## 2. 再评估：三处过度表述要收回

上一版（我的早期分析）把 P1 说成「比稀疏奖励更直接的失败原因」，**过头了**。以下三点属实，据此降级 P1：

1. **`temperature_init=1e-2` 不是 WA2 fork 独有魔改**，而是 hil-serl 官方 `launcher.make_sac_pixel_agent_hybrid_*` 的惯例（真机像素 SAC 常用更小 α，避免一上来动作乱飞）。我之前拿 `create_pixels` 默认 1.0 对比 launcher 入口，把「库默认 vs 真机入口」误判成「上游正常 vs 你们改坏」——**判断错误，收回**。
2. **floor 让 α 迅速脱离 0.01**：循环顺序是 `update(Lagrange 下压) → ensure_min_temperature(托到 0.05)`，有效噪声很快按 √0.05≈0.22 量级跑，不是全程卡在 √0.01=0.1。冷启动只影响 `R13_RLPD_START` 首次 publish 之后的一小段窗口。
3. **HIL 早期多样性主要靠人接管，不靠 SAC 高斯噪声**；「RLPD 靠 online 噪声超越 demo」的纯 RL 叙事在 HIL-SERL 里权重本来就低。

## 3. 补充：floor 是「双刃」（这是上一版文档没覆盖的点）

文档用「floor 托回地板」来反驳 P1 是对的，但**正是这个 floor 触发了另一个问题（P2）**：

- 每次 `ensure_min_temperature` 把 α 顶回地板时，都调用 `set_sac_temperature`，在 `r13_learner_train.py:170` 执行 `txs["temperature"].init(new_params)` **重建温度 Adam 状态**；
- 死奖励下熵长期 > `target_entropy=-3.0`，Lagrange 每步把 α 往下压、floor 每步又顶回来 → **温度优化器每步被清零**。

净效果：**温度自调节（Lagrange multiplier）被架空，α 恒等于地板值 0.05，`target_entropy` 实际失效**。这不是「bug」，而是「手动固定温度」的一种非标准实现；是否成立只取决于 0.05 这个固定值是否合适。

**定级**：P1（init 偏冷）与 P2（温度自调节被关）都应归为次要；它们与稀疏奖励是叠加关系、不是替代关系，也不能用来否定已修的稀疏奖励路径。

## 4. 温度线的最终结论

- 机制真实性：高（代码与公式都对）。
- 是否本轮主根因：**低～中**（被 floor + HIL 干预冲淡）。
- 重启前是否必须先改：**不必**。
- 是否值得当调参项留：值得，成本低（对齐 `temperature_init` 与 `min_temperature`，或抬 floor 到 0.1~0.5；**不要只改 `r13_learner_train.py:40` 的 `SAC_TEMPERATURE_INIT` 打印常量**，真正起作用的是 launcher 里的硬编码）。

## 5. 重启训练真正要盯的：新 demo 是否真的进 buffer（优先级最高）

上一轮修复的是「demo 奖励被清零」→ 已改为末端 `reward=1`（`demo_io.py:213-234`，数据逐字节验证通过：新 bundle 末端 reward=1、7D、夹爪边沿齐全）。**但这条修复能否生效，卡在数据链路的两处缓存/哈希上；处理不好会静默地又训到旧 demo，等于白修。**

关键链路（已确认）：

```
build_r13_manifest.py:56   demo_pkl_sha256 = sha256_file(demo)        # --demo-pkl 必填(第97行)
        ↓
r13_learner_train.py:770   demo_sha = manifest.get("demo_pkl_sha256")
        ↓
r13_learner_train.py:776   try_load_demo_buffer(cache_dir, demo_buffer, demo_pkl_sha256=demo_sha)
```

即 **demo buffer 的缓存 key = manifest 里的 `demo_pkl_sha256`**。两个风险叠加：

1. manifest 没重打 → `demo_sha` 还是旧 hash；
2. 旧 hash 下若留着上次的缓存 → `try_load_demo_buffer` **HIT 旧缓存**（reward 被清零的旧 demo），直接跳过 `_insert_demo_episodes`（第 779 行）。

结果：新 demo 躺在磁盘上，但训练吃的是旧 buffer。

### 重启前三条确认清单（只核对，不改代码）

| # | 项 | 怎么确认 |
|---|---|---|
| 1 | 两端重打 manifest，`--demo-pkl` 指向**新 bundle 的 `demo.pkl`** | 重跑 `build_r13_manifest.py --demo-pkl <新bundle>/demo.pkl --role actor/learner ...`；两端 `demo_pkl_sha256` 必须一致 |
| 2 | 强制重建 demo buffer cache | 启动时传 `--rebuild_demo_buffer_cache`，或删缓存目录（默认 `output/demo_buffer_cache`），避免 HIT 旧 demo |
| 3 | `--demo_path` 指向**新 bundle 目录** | `resolve_bundle_dir(args.demo_path)` 应落到 `.../wa2_bottle_pick_20_success_7d_7b67fc1e` |

> 小脆弱点备忘：manifest 哈希的是 3GB 的 `demo.pkl`，learner 实际读的是 `episodes/epXXX.pkl`（`require_episode_pkls`），二者是代理关系——只要按第 1 条重打 manifest 指向新 `demo.pkl`，cache 就能正确失效，这个代理关系不影响本次重启。

## 6. 一句话总结

P1（温度初始化偏冷）机制真实但只是次要调参项，上版分析高估了它，正确级别与「稀疏奖励」无关、且不否定已修的稀疏奖励路径；floor 顺带关掉了温度自调节（同样次要）；**重启前真正决定成败的是第 5 节的三条——保证「新 demo（末端 reward=1）确实进 buffer」**，否则重启大概率还是老结局。
