## 1. 结论摘要

| 问题 | 结论 |
|---|---|
| 只关 Actor 休息、Learner 挂着再开 Actor | **旧代码下新局数据经常传不进去**（空上传 + pending 顶满丢数） |
| 是否和网络代理有关 | **无关**（LAN ZMQ；`status_rtt` 正常） |
| 是否「所有干预都没进 Learner」 | **否**；有过大量成功入库，但也有过整段 Actor 进程白跑 |
| 能否只重启 Actor 续传 | **现已可**：握手后 `UPLOAD_CURSOR_ALIGN` 对齐 Learner `last_update_id` |
| Learner 重启另丢什么 | 内存里的 online + **已追加的干预 demo** 不进 `demo_buffer_cache`，重开后回到缓存基线 |

---

## 2. 机制（为何会坏）

TrainerServer 的 `last_update_id_map` 随 Learner 进程单调递增。  
Actor 每次启动本地 `seq_id` 从 0 计。若 Learner 不重开：

1. 服务端游标例如已到 `14692`  
2. 新 Actor 本地最新只有几千  
3. `peek_batch_after(server_id)` 认为无新数据 → `update_ok=True` 但 **sent=0**  
4. `confirm` 报 `server ahead of client for actor_env_intvn`  
5. `pending` 堆到 2048 → `UPLOAD_DROP_UNACKED` 狂涨 → 本进程数据丢失

## 3. 历史入库量排查（可核对的证据，非精确全账）

没有跨天、跨进程的完整「每条干预是否入库」审计日志；只能用 **峰值快照 + 丢数计数** 做下界/上界。

### 3.1 曾成功进过 Learner 的量（证明「不是全程没传」）

| 来源 | ONLINE / INTVN（约） | 说明 |
|---|---|---|
| `调试日志/0821调试日志.md` | **26558 / 24948** | 某一 Learner 长进程峰值；当时已到 `checkpoint_10000` |
| 0824 当日 `status.json`（instance `6bb450f2…`） | **14710 / 14387** | 今日重开 Learner 后再次涨上来的峰值；其后因 Actor 单端重启再次卡住 |
| Demo 文件 | `DEMO_FILE_N=29951` | 20 局 7D demo，在 `demo_buffer_cache` 里，重启可恢复 |

### 3.2 明确丢失 / 未进入当前 Learner 内存的部分

| 类型 | 证据 | 含义 |
|---|---|---|
| Actor 单端重启后的空上传段 | 终端长期 `confirm_ok=False` + `server ahead` + `server_*_count` **钉死** | 该 Actor 进程后半段 **未入库** |
| 队列顶满丢弃 | 例如 `UPLOAD_DROP_UNACKED env≈6500 intvn≈6200` | 至少数千条在 Actor 本地被挤掉 |
| 末次 `actor_status.json` | `ONLINE_N=8566`，`PENDING=2048/2048`，Learner 仍钉在 14710 | 本进程八千多步里，错位之后基本没进服 |
| Learner 重启 | 0821 峰值 ~2.6 万 online **不随 ckpt 落盘**；干预追加的 demo 也不写回 `demo_buffer_cache` | 权重还在，**那一进程的 buffer 内容没了**；重开后从 cache≈29971 + 新上传重建 |

### 3.3 对「训练数据是否非常有限」的判断

- **权重**（`checkpoint_10000`→`11000`→更高）：吃过 demo + 若干长进程里成功上传的 online/intvn（峰值曾到两万级）。  
- **不等于**「你现场每一次干预都进了当前 buffer」。  
- 多次「Learner 挂着、只重启 Actor」→ 每次错位后的整段休息后开训，**大概率白跑**。  
- 每次 **Learner 重启**→ 当日内存里已攒的 online/干预追加 demo **清零**（cache 只保原始 20 局）。

**无法精确还原「总共干预了多少条、丢了百分之几」**——缺少连续 `STORE`/`UPLOAD` 归档。能确定的是：**有过大量成功入库，也有过系统性整段丢失；你的担心成立，但不是「ckpt 完全没见过真机数据」。**

## 5. 操作约定（更新）

| 场景 | 做法 |
|---|---|
| 中途休息只关 Actor | **可以**；回来直接开 Actor（需已含今日对齐补丁） |
| 旧 Actor 代码（无 `UPLOAD_CURSOR_ALIGN`） | 仍必须先重启 Learner 再开 Actor |
| Learner 重启 | 仍会丢内存 online/追加 intvn；`--resume` + `DEMO_BUFFER_CACHE=hit` 只恢复权重与原始 demo |
| 健康检查 | `UPLOAD_CURSOR_ALIGN` 出现；`confirm_ok=True`；计数上涨；无持续 `server ahead` |

## 6. 上传背压误杀 `network_loss`（同日补丁）

**现象：** `confirm_ok=True` 但 `update_ok=False` + `pending=2048` + `UPLOAD_DROP_UNACKED` → 立刻 `FAULT_REASON=network_loss`（Learner 仍活着）。

**落地（推荐方案 A + B/C）：**

| 改动 | 行为 |
|---|---|
| gap 容忍上传 | 顶满丢旧条后从本地队首继续发，Learner 游标跳过空洞；打 `UPLOAD_GAP_SKIP` |
| soft fail | `update_ok=False` 且 `confirm_ok=True` → `UPLOAD_SOFT_FAIL`，**不计**入断网看门狗 |
| UploadWatchdog | 连续失败阈值 **5**；仅 `confirm` 也失败（真达不成 Learner）才累计 |

仍可能丢最旧未确认数据，但不应再因背压整段停训。真断网仍 fail-closed。

## 8. Buffer 落盘（Learner 可重启恢复）

路径（默认在 `$R13_RUN` 下）：

| 目录 | 内容 |
|---|---|
| `demo_buffer_cache/` | demo + **已追加干预**（周期性覆盖） |
| `online_buffer_cache/` | online replay |

行为：

- **默认只在正常终止 Learner 时落盘一次**（`BUFFER_SNAPSHOT reason=shutdown`），不再每个 checkpoint 写 ~GB 级图像库。  
- SAC `checkpoint_*` 仍按 `--checkpoint-period`（默认 1000）保存；终端用 **`CKPT` 进度条**（`0→period`，旁注 `within/period` + `step=`）代替逐步刷 `GRASP_CRITIC_UPDATE`。  
- **中断（Ctrl+C）**：先写 `CHECKPOINT_STEP=… reason=interrupt`（当前 step，非必须整千），再异步/阻塞落盘 buffer；落盘过程显示可观察进度条，**再按一次 Ctrl+C** 可取消未完成的 dump（不污染已原子 rename 的旧缓存）。  
- 可选：`--buffer-snapshot-every N` 额外按步周期落盘；`--no-buffer-snapshot` 连停机也不写。  
- `--resume` 时加载 `online_buffer_cache` + 扩大后的 `demo_buffer_cache`（可带 `intvn_cached=…`），并从最近 checkpoint（含 interrupt）继续。  
- `INTVN_N` 基线为原始 **`demo_n`（文件局）**。  
- `STORE` 日志节流约 5s 一次，避免打断进度条。

停机务必等 `BUFFER_SNAPSHOT reason=shutdown`（或主动二次中断取消）→ `R13_LEARNER_STOPPED`。

笔记本需同步  
`HILSERL_Learner/src/hilserl_wa2/scripts/r13_learner_train.py`。
