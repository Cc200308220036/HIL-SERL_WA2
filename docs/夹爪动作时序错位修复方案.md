# HIL-SERL-WA2 夹爪动作时序错位修复方案

## 1. 文档目的

本文档定义 WA2 上 HIL-SERL 7D 混合动作中，夹爪动作执行后没有重新采集 `next_obs` 和计算 `reward` 的时序错位问题，并给出待审核的修改方案、两端边界和验收标准。

本方案只修复 Actor 端的物理执行与 transition 时序语义，不改变 Learner 端 Grasp DQN 的 Bellman 更新公式，不改变 10 Hz 高层决策、50 Hz Servo 和每个高层动作最多 5 个 Servo tick 的时间契约。

---

## 2. 当前问题

### 2.1 当前执行顺序

当前 `WA2GraspActionWrapper.step()` 大致按以下顺序执行：

```text
obs_t
→ self.env.step(arm_6d)
→ 完成 5 个 Servo tick
→ 获得 next_obs、reward、terminated、truncated
→ 解析夹爪动作
→ request_hand(grasp/release)
→ 将 grasp_command 写入 info
→ 返回夹爪执行前已取得的 next_obs
```

关键代码位于：

- `catkin_ws/src/hilserl_wa2/wrappers/grasp_action.py`；
- 先调用 `self.env.step(arm)` 取得观测和基础 reward；
- 后调用 `_fire_hand()` 执行夹爪；
- 最终返回的仍是夹爪执行前的观测。

### 2.2 实际存储语义

当 Actor 将成功夹爪命令重写到 `actions[6]` 后，replay 中实际存储的样本近似为：

```text
observations      = 动作前状态
actions           = [6D 连续动作, 已执行夹爪动作]
next_observations = 夹爪执行前状态
rewards           = 夹爪执行前观测对应的奖励
```

而 Grasp DQN 需要的语义是：

```text
(s_t, a_gripper_t, r_t, s_(t+1))

s_(t+1) 必须是 a_gripper_t 已经完成后的状态。
```

当 `next_observations` 中的 `hand_joints`、腕部图像和头部图像尚未反映夹爪动作时，Grasp DQN 无法正确学习“在当前状态执行 grasp/release 后会发生什么”。

### 2.3 reward 也随之错位

当前 wrapper 嵌套顺序为：

```text
WA2Env
→ WA2SpacemouseIntervention
→ WA2GraspActionWrapper
→ SERL observation wrappers
→ WA2RewardClassifierWrapper
```

Reward Classifier 位于 Grasp wrapper 外层。如果 Grasp wrapper 返回夹爪执行前的观测，Classifier 也会使用该旧观测判定成功与 reward。

这里的“reward 错位”不表示 grasp 或 release 当步应该获得正奖励。本任务使用终点稀疏奖励：正常的 grasp 当步和 release 当步 reward 都应为 `0`。修复的要求是 Classifier 判定所使用的观测必须与 transition 中的 `next_observations` 一致，且两者都位于夹爪命令完成之后。

### 2.4 完整任务与终点奖励语义

WA2 当前任务不是“夹住或抬起即成功”，而是完整的抓取、搬运、放置和撤离任务：

```text
初始夹爪张开
→ 手臂逼近目标瓶子
→ 关闭夹爪（actions[6] = +1）
→ 搬运期间保持夹爪关闭（actions[6] = 0）
→ 到达目标放置位置
→ 张开夹爪（actions[6] = -1）
→ 撤离期间保持夹爪张开（actions[6] = 0）
→ 手臂移动到安全位置
→ 瓶子稳定站立
→ reward = 1，terminated = true
```

因此，一条完整成功演示至少必须包含一次 grasp `+1` 和一次 release `-1`，且 grasp 必须早于 release。现有对成功 demo 中非零夹爪边沿的存在性检查方向是正确的，本修复不应删除该约束。

需要额外确保：

- 初始状态、逼近阶段、grasp 当步、搬运阶段和 release 当步均不得给出成功奖励；
- 仅当瓶子完成放置并稳定站立、手臂已撤离到安全位置时才给出唯一的 `reward=1`；
- 夹爪执行后重新计算 reward 的含义是重新评估 post-hand state，正常结果仍应为 `0`。

---

## 3. 修复目标

修复后，一次 7D 高层动作必须形成如下完整事务：

```text
1. 采集 obs_t
2. 策略产生 [arm_6d, gripper_1d]
3. arm_6d 执行最多 5 个 Servo tick
4. gripper_1d 在该高层步内最多执行一次
5. 等待夹爪服务完成并确认手部反馈
6. 重新采集 post-hand next_obs
7. Classifier 使用该 post-hand next_obs 计算 reward
8. 只构造和上传一条 7D transition
```

对于正常 grasp/release 事件，第 7 步的预期结果是 `reward=0`。只有完整任务的最后安全撤离与瓶子稳定状态允许产生 `reward=1`。

最终 transition 应满足：

```text
(
    obs_t,
    [executed_arm_6d, executed_gripper_1d],
    reward(post_hand_next_obs),
    post_hand_next_obs,
    done
)
```

本次修复不允许通过再次调用 `env.step()` 获得新观测，因为第二次 `env.step()` 会额外执行另一个 5-tick Servo 窗口、重复增加环境步数，并产生新的时序错误。

## 4. 总体修改方案

## 4.1 WA2Env 增加公开的只读观测接口

当前 `WA2Env` 已有私有 `_get_obs()`，建议在 Actor 端增加公开的只读观测接口，例如：

```python
def observe(self):
    """采集当前机器人和相机观测，不执行动作。"""
```

该接口必须满足：

- 不发布 ServoL；
- 不启动新的 Servo action window；
- 不增加 `_step_count`；
- 不修改 `_last_applied`；
- 不触发新的 reward 计算；
- 返回值必须满足现有 `observation_space`；
- 最好同时提供状态和图像 freshness 信息。

不建议 Grasp wrapper 长期直接调用私有 `_get_obs()`，否则 wrapper 将与 `WA2Env` 内部实现强耦合。

## 4.2 增加夹爪反馈确认

`request_hand()` 返回成功不一定等价于 ROS `hand_joints` 监视数据已经更新。因此，建议在夹爪服务完成后等待手部反馈靠近目标值：

```text
norm(hand_joints - hand_target) <= hand_tolerance
```

可采用以下任一形式：

```python
observe_after_hand(target, timeout_s, tolerance)
```

或由 Grasp wrapper 在有界时间内轮询 `observe()`。

反馈确认必须：

- 有明确超时时间，不允许无限阻塞；
- 使用与实际 grasp/release target 匹配的容差；
- 记录等待时间和最终误差；
- 能区分“服务明确失败”和“服务返回成功但反馈未确认”。

## 4.3 Grasp wrapper 在夹爪完成后替换 next_obs

建议将 `WA2GraspActionWrapper.step()` 改为如下等价语义：

```python
obs_after_arm, reward, terminated, truncated, info = self.env.step(arm)

if hand_fired:
    hand_result = self._fire_hand(command)

    if hand_result is confirmed:
        next_obs = base_env.observe_after_hand(...)
        executed_gripper = +1 or -1
    else:
        next_obs = base_env.observe()
        transition_valid = False
else:
    next_obs = obs_after_arm
    executed_gripper = 0

return next_obs, reward, terminated, truncated, info
```

关键约束：

- `self.env.step(arm)` 只能调用一次；
- 一个高层步仍只能执行最多 5 个 Servo tick；
- 夹爪服务最多调用一次；
- hold 动作不需要额外刷新观测；
- 夹爪执行后必须用新观测替换 `obs_after_arm`；
- 只有完成执行并通过反馈确认的夹爪命令才可记录为 `+1/-1`。

## 4.4 夹爪动作后强制执行 Classifier

当前 Classifier 支持 `decimate` 和 SpaceMouse session 内降采样。夹爪动作是离散状态切换事件，不应在该步跳过推理。

建议在 `WA2RewardClassifierWrapper.step()` 中增加等价逻辑：

```python
force_infer = bool(info.get("hand_fired"))
run = force_infer or self._should_run_infer(sm_session=sm)
```

因此：

- 普通连续移动仍可按原规则降采样；
- grasp/release 后必须用 post-hand observation 重新计算成功概率；
- reward 与 transition 中的 `next_observations` 保持同一时刻语义。

## 4.5 无效 transition 必须 fail-closed

对于夹爪执行结果或 post-hand observation 无法确认的情况，Actor 不应将它伪装成 hold 动作上传。

建议 Grasp wrapper 输出：

```text
transition_valid = false
hand_feedback_ok = false
interrupted_by = hand_feedback_timeout | hand_exec_failed
```

Actor 主循环检测到该状态后：

1. 禁止上传当前 transition；
2. 触发 fail-closed；
3. 停止自动策略执行；
4. 要求人工确认实际手部状态或执行 reset。

原因是夹爪可能已经部分执行。如果记录为 `action[6]=0`，replay 将变成“记录为 hold，物理状态却已改变”。

---

## 5. 夹爪失败语义

| 执行情况 | `actions[6]` | transition 处理 |
|---|---:|---|
| hold | `0` | 正常上传 |
| grasp 服务成功且反馈确认 | `+1` | 使用 post-hand observation 上传 |
| release 服务成功且反馈确认 | `-1` | 使用 post-hand observation 上传 |
| 服务明确失败且可确认物理状态未变 | `0` | 原则上可记录，真机阶段建议仍中止 |
| 服务结果不确定 | 不可信 | 禁止上传，fail-closed |
| 手部反馈超时 | 不可信 | 禁止上传，fail-closed |
| 人工夹爪动作成功 | `+1/-1` | 同时进入 online 和 intervention buffer |
| 人工夹爪动作失败 | 不可信 | 禁止上传，人工确认/reset |

---

## 6. 建议新增的可审计字段

建议在 `info` 和 Actor 运行日志中增加：

| 字段 | 含义 |
|---|---|
| `hand_requested_command` | 策略或人工请求的 grasp/release/hold |
| `hand_executed_command` | 最终确认执行的命令 |
| `hand_fired` | 本高层步是否调用夹爪服务 |
| `hand_ok` | 夹爪服务返回是否成功 |
| `hand_feedback_ok` | 手部反馈是否到达目标容差 |
| `hand_feedback_error` | 最终手部目标误差 |
| `hand_execution_duration_s` | 夹爪服务耗时 |
| `hand_feedback_wait_s` | 等待手部反馈的时间 |
| `post_hand_obs_refreshed` | 是否在夹爪后重新采集观测 |
| `post_hand_obs_fresh` | 夹爪后观测是否通过 freshness 检查 |
| `transition_valid` | 当前 transition 是否允许上传 |
| `high_level_execution_duration_s` | Servo 窗口加夹爪执行/等待的总时间 |

这些字段不一定全部进入 replay tensor，但必须能够从 Actor 日志或审计文件中还原一次高层动作的完整物理执行过程。

## 7. Actor/Learner 边界

## 7.1 Actor 端实际执行修改

需要修改的主要文件：

```text
catkin_ws/src/hilserl_wa2/envs/wa2_env.py
catkin_ws/src/hilserl_wa2/wrappers/grasp_action.py
catkin_ws/src/hilserl_wa2/wrappers/reward_classifier.py
catkin_ws/src/hilserl_wa2/scripts/r13_actor_train.py
```

职责分别为：

- `wa2_env.py`：提供无动作的观测快照及夹爪反馈确认能力；
- `grasp_action.py`：执行夹爪，获得 post-hand observation，设置有效性标记；
- `reward_classifier.py`：在夹爪事件后强制使用新观测推理；
- `r13_actor_train.py`：对不可信 transition 禁止上传并 fail-closed。

## 7.2 Learner 端不修改训练公式

本问题不需要修改：

```text
Grasp DQN Bellman target
SAC 连续 Actor/Critic 损失
RLPD online/demo 50:50 抽样
checkpoint 参数树结构
```

但 Actor 端共享的 Env/wrapper 语义文件需要镜像到 Learner 工作区的同路径文件，以保持：

- fake env 和 action/observation space 构造一致；
- Actor/Learner manifest 一致；
- `source_tree_sha256` 一致；
- 部署包不出现同名代码两套语义。

这种镜像仅用于版本和接口一致，夹爪物理执行仍完全属于 Actor 端。

## 8. 不应采用的方案

### 8.1 夹爪后再调用一次 env.step

不可接受，因为会：

- 再执行一个 5-tick Servo 窗口；
- 一次策略动作对应两个环境步；
- 增加 `_step_count`；
- 可能额外触发 reward/done；
- 破坏阶段三时间契约。

### 8.2 仅修改 actions[6]，不更新 next_obs

这正是当前问题，无法满足 DQN transition 语义。

### 8.3 所有失败命令都记录为 hold

如果夹爪已部分动作，记录为 hold 会引入错误的物理标签。结果不确定时应丢弃 transition 并 fail-closed。

### 8.4 只在 Learner 端修改 Grasp DQN

Learner 无法从已错位的 `(s, a, s')` 中还原真实夹爪后状态。必须先在 Actor 物理执行边界修正数据。

## 9. 测试与验收标准

## 9.1 单元测试

需要覆盖：

1. `grasp=+1`：返回的 `next_obs.hand_joints` 靠近 grasp target；
2. `release=-1`：返回的 `next_obs.hand_joints` 靠近 release target；
3. `hold=0`：不调用夹爪服务，不进行额外观测刷新；
4. 夹爪服务失败：不产生错误的非零夹爪标签；
5. 夹爪反馈超时：`transition_valid=false`；
6. SpaceMouse 右键夹爪：同样获得 post-hand observation；
7. 夹爪后 Classifier 必须推理，不受 decimate 跳步影响；
8. 每个高层步 `env.step()` 只调用一次；
9. `_step_count` 只增加一次；
10. 不产生第六个 Servo tick。
11. grasp 当步 post-hand observation 正确，但 reward 仍为 `0`；
12. release 当步 post-hand observation 正确，但 reward 仍为 `0`；
13. 只有模拟“已放置、已撤离、瓶子稳定”的终点观测才返回 `reward=1`。

## 9.2 fake env 集成验收

对一次 `grasp=+1` 必须同时满足：

```text
servo_ticks_requested == 5
servo_ticks_executed == 5
hand_service_call_count == 1
transition.actions[6] == +1
transition.next_observations.hand_joints ≈ grasp_target
classifier_input == transition.next_observations
transition.rewards == 0
env_step_count_delta == 1
transition_valid == true
```

`release=-1` 需按 release target 通过同等检查，且 release 当步 `transition.rewards` 也应为 `0`。

## 9.3 Actor 容器离线/dry-run 验收

需确认：

- 现有 5-tick Servo 测试继续通过；
- 夹爪后观测刷新不调用 ROS 动作服务两次；
- 夹爪服务延迟不会使 Servo 窗口继续发布第六 tick；
- 夹爪服务期间 Servo latch 处于安全 hold/撤销状态；
- 无效夹爪反馈会阻止 transition 上传。

## 9.4 真机时序验收

建议日志能够证明：

```text
t_obs_before
< t_servo_window_end
<= t_hand_command_done
<= t_post_hand_obs
<= t_classifier
<= t_transition_store
```

正常 grasp/release 事件必须严格满足：

```text
servo_ticks_executed <= 5
hand_service_call_count == 1
post_hand_obs_refreshed == true
post_hand_obs_fresh == true
hand_feedback_ok == true
transition_valid == true
```

## 9.5 Buffer 数据验收

对新 buffer 中所有 `actions[6] != 0` 的 transition 检查：

### grasp `+1`

```text
distance(next_hand_joints, grasp_target)
<
distance(obs_hand_joints, grasp_target)
```

### release `-1`

```text
distance(next_hand_joints, release_target)
<
distance(obs_hand_joints, release_target)
```

### 完整成功 episode

对每条成功 episode 检查：

```text
初始 hand state = released
至少一次 actions[6] = +1
至少一次 actions[6] = -1
第一次 +1 早于用于最终放置的 -1
grasp transition reward = 0
release transition reward = 0
中间搬运 transition 的夹爪保持关闭
撤离 transition 的夹爪保持张开
只有最后安全撤离且瓶子稳定的 transition reward = 1
最后一条 transition dones = true, masks = 0
```

如果任务允许失败后重抓，episode 可以包含多个 grasp/release 边沿，但最终 reward 仍必须由完整放置与安全撤离条件触发，不能仅由“夹爪已打开”触发。

建议验收门槛：

- 100 次夹爪事件中无重复服务调用；
- 所有有效非零夹爪 transition 均使用 post-hand observation；
- 夹爪反馈确认率应接近 100%；
- Classifier 输入图像与 transition `next_observations` 图像哈希一致；
- 任何无法确认物理结果的样本都不得进入 replay。
- 成功 episode 中 grasp/release 边沿顺序符合完整任务状态机；
- episode 起始、grasp 当步和 release 当步不得出现误报的 `reward=1`。

## 10. 时间尺度影响

普通 hold 步仍维持：

```text
Policy/transition: 10 Hz
Servo: 50 Hz
Servo ticks per action: 5
```

当发生 grasp/release 时，高层 step 可能因夹爪服务和反馈等待超过 100 ms。这属于低频离散事件的执行延迟，不应通过增加 Servo tick 或在后台继续积分上一动作来补偿。

需记录：

```text
high_level_execution_duration_s
= servo_execution_duration_s
+ hand_execution_duration_s
+ hand_feedback_wait_s
```

夹爪服务期间，Servo 窗口必须已经正常结束并撤销，不得因 Actor 主循环阻塞而继续执行上一个连续动作。

### 10.1 终点稀疏奖励与 discount 审计

本任务只在完整放置和安全撤离后给出一次 reward。在 10 Hz 高层时间尺度下，grasp 与终点 reward 之间可能相隔上百个 transition。当 `discount=0.98` 时：

```text
0.98^105 ≈ 0.12
0.98^27  ≈ 0.58
```

这表示早期 grasp 动作的终点奖励信用较弱，必须依赖连续、正确的 TD bootstrapping 向前传播。夹爪边沿上错位的 `next_observations` 会直接破坏这条信用链，因此必须先修复 transition 语义，再根据新数据评估 discount。

本方案不默认修改 `discount=0.98`。在 post-hand transition 正确、Classifier 终点判定可靠且新 buffer 已形成后，再独立审计：

- reward 向 grasp 状态的 Q 值传播是否稳定；
- 不同阶段的 grasp/release/stay Q 间隔是否合理；
- 是否需要调整 discount，而不是用更高 discount 掩盖错误数据。

## 11. 实施顺序

1. 冻结 post-hand observation、反馈容差和超时语义；
2. 在 `WA2Env` 实现无动作的公开观测快照接口；
3. 在 Grasp wrapper 中实现夹爪后反馈确认和 next_obs 替换；
4. 在 Reward Classifier 中实现夹爪事件强制推理；
5. 在 Actor 主循环实现无效 transition 禁止上传；
6. 补充单元测试和 fake env 集成测试；
7. 镜像共享语义文件到 Learner 工作区；
8. 重建两端 manifest，确认哈希一致；
9. 在 Orin 容器内进行 dry-run 和小规模真机验收；
10. 采集新数据并审计非零夹爪 transition；
11. 通过数据验收后，再恢复正式 HIL 训练。

## 12. 旧 buffer/checkpoint 兼容性

旧 buffer 中所有 `actions[6] != 0` 的 transition 都可能存在“夹爪动作已记录，`next_observations` 却仍是夹爪前观测”的错位。这类问题不能仅靠后处理从旧观测中恢复真实 post-hand state。

旧 buffer 的风险来自夹爪边沿 transition 的 `(s, a_gripper, s')` 时序错位，不是因为成功 episode 同时包含 grasp 和 release。对当前完整抓取—放置—撤离任务，合格的成功数据本来就应包含按正确顺序发生的 `+1 grasp` 和 `-1 release`。

因此，完成修复后应将新 transition schema/config hash 与旧数据隔离。是否保留旧数据中 `actions[6]==0` 的连续动作样本，需要单独进行数据审计，不应在本修复中默认混用。

checkpoint 5000 可作为历史审计基线，但它已经使用时序错位的夹爪 transition 训练，不能因为修改了 Actor 执行顺序就自动视为新语义下的合格起点。

## 13. 方案审核决策点

实施前需要确认：

1. grasp/release 保持“5 个 arm Servo tick 后执行”的顺序宏动作语义，并确认该顺序与真机抓取和放置节拍一致；
2. grasp/release target 容差应使用哪个已验收参数；
3. 夹爪反馈确认超时时间；
4. 服务返回失败但能确认状态未变时，是丢弃 transition 还是记录 hold；
5. 夹爪事件后 Classifier 是否无条件强制同步推理；
6. 旧 buffer 和 checkpoint 的隔离策略；
7. 新 transition schema 版本号和两端 manifest 更新方式。
8. 任务配置和交付文档中的任务名称是否从“抓瓶抬起”统一为“抓取—搬运—放置—安全撤离”，避免成功条件歧义。

在上述决策点确认前，本文档仅作为待审核实施方案，不代表已完成代码修改或真机验收。
